# Design — How create-ai-builder composes create-project-system

**Status:** design (informs create-ai-builder task 14 / target-composition).
**Scope:** how the task-system generator (this repo) and the agent-pipeline
generator (create-ai-builder) compose, both for create-ai-builder *itself* and
for the platform repos it installs an ai-builder into.

## Two layers, two owners

An installed ai-builder is **two stacked layers** with **different owners and
different sources**:

| Layer | What | Owner / source | How it lands |
|---|---|---|---|
| **1. Task system** | `project/tasks/` scripts + `task-env.sh`/`task-config.sh`, `docs/` (USING.md, README, task-manager), the `task-system` **skill**, the `## Task tracking` **CLAUDE.md** block | **create-project-system** (this repo) — single source | `generate.sh --tasks-dir project/tasks --with-status --with-skill --inject-claude-md` |
| **2. Pipeline overlay** | the 7 pipeline scripts (`advance-pipeline`, `new-pipeline-*`, `on-task-complete`, `set-current-job`, `check-stop-after`, `pipeline-build-template`) + orchestrator/roles/machines | **create-ai-builder** — its own hand-maintained code | copied/installed **on top of** layer 1 |

**The pipeline layer does NOT come from `generate.sh`.** `generate.sh` only ever
emits the task-system layer. Layer 2 is create-ai-builder's, laid on top.

## The indirections (why this needs a doc)

create-ai-builder is **both a consumer and a producer** of the task system:

- **Indirection A — for itself.** create-ai-builder's own `project/tasks/` is
  generated by create-project-system (task 09). It is a *consumer*.
- **Indirection B — for its targets.** When create-ai-builder installs an
  ai-builder into a platform repo, that target *also* needs the task system —
  because the pipeline is driven by tasks. create-ai-builder is a *producer*, but
  it should **delegate** layer 1 to `generate.sh` rather than reproduce it.

### Current mechanism (to be replaced)

`target/setup-project.sh` copies create-ai-builder's **own**
`project/tasks/scripts/` into the target ("canonical source, one copy to
maintain"). After task 09 those scripts are themselves generated, so the path is
a **copy-of-a-copy** with two drift points:

```
create-project-system  ─generate→  create-ai-builder/project/tasks/scripts  ─cp→  target
```

`setup-project.sh` also hand-re-implements epic scaffolding + CLAUDE.md init that
`generate.sh` already does (and does better: decoupled paths, worktree-aware
root, non-destructive regen, sentinel CLAUDE.md, layers).

### Target mechanism (delegate, one hop)

```
create-project-system  ─generate→  target/project/tasks   (layer 1, from source)
create-ai-builder      ─overlay→   target pipeline scripts (layer 2, its own)
```

`setup-project.sh` becomes: **(1)** call pinned `generate.sh` for layer 1
(which also installs the skill, USING.md, and the CLAUDE.md block — all three
must be present in the target), **(2)** overlay the pipeline scripts +
orchestrator config.

## Pinned version (decided)

create-ai-builder **pins a specific create-project-system version** so target
installs are reproducible and the layer-1 contract is explicit. Mechanism (git
submodule at a pinned commit, or a vendored snapshot at a tag — pick in task 14).
The pin is bumped deliberately, like any dependency; a target's task layer is
then exactly reproducible from `(pinned create-project-system version, flags)`.

## What generate.sh must deliver to a target (checklist for layer 1)

- [ ] `project/tasks/` machinery (decoupled) + `project/status/`
- [ ] `project/tasks/docs/USING.md` (+ README, task-manager)
- [ ] `.claude/skills/task-system/SKILL.md` (`--with-skill`)
- [ ] the `<!-- task-system:begin/end -->` **CLAUDE.md** block (`--inject-claude-md`)

All four already come from a single `generate.sh` invocation with
`--with-status --with-skill --inject-claude-md` — nothing new to build in this
repo; the work is on the create-ai-builder side (task 14).
