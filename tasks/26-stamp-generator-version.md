# Task 26 — Stamp the generator version into every generated install

**Type: feat.** Nothing in a generated task-system records which version of
`create-project-system` produced it, so drift between installs is only
discovered when a consumer crashes on it. Surfaced 2026-08-06 alongside task 25;
the same investigation produced both.

## Why

`v0.1.0` is cut and pinnable (task 23), `v0.2.0` will carry a breaking field
rename (task 19) and a new flag (task 15). From that point on, installs in the
wild legitimately differ — and today there is **no way to ask an install what it
is**. Consequences already observed:

- `create-ai-builder` has no `inbox/` while `captains-log` does (task 25). A
  consumer hitting that cannot tell an old install from a broken one.
- The workspace's `replan` probe scrapes `list-tasks.sh`'s human output and
  assumes the folder vocabulary. With no version to branch on, a vocabulary
  change and an error look identical from outside. (This is the same pressure
  behind the `--json` request in triage — a machine-readable interface and a
  version stamp are complements: the stamp says *which contract*, the JSON says
  *the data under it*.)
- Task 25's backfill needs to know nothing about versions to work, but a
  consumer deciding *whether to regenerate* does.

The precedent is already in the portfolio: `create-git-workspace` writes a
managed block footer naming the generator version, with the canonical value in
`.workspace/config.yml`. This repo emits nothing equivalent — the only
version-ish text in `generate.sh` is prose in the upgrade comment
(`generate.sh:31`, `:65`, `:71`).

## Where the stamp goes

**`task-config.sh` is the natural home.** It is already generated from
`src/config/task-config.sh.in`, already marked *"GENERATED by
create-project-system. Do not hand-edit"*, already the single source of truth
for mount configuration, and already sourced by `task-env.sh` — so every script
gets the value for free, and any consumer can read it with one `grep`:

```sh
GENERATOR_VERSION="{{GENERATOR_VERSION}}"
```

## Decisions to make

- **Where the version comes from.** This repo has no `VERSION` file; the version
  exists only as a git tag. Options: (a) checked-in `VERSION` file at the repo
  root, read by `generate.sh`; (b) `git describe --tags` at generate time.
  **Lean: (a)** — `git describe` breaks when the generator is vendored as a
  tarball or run from a shallow/detached checkout, yields different strings on
  tagged vs. untagged commits, and would make golden output depend on repo
  state. A file is boring and deterministic. The cost is remembering to bump it
  when tagging, which belongs in the release checklist task 23 established.
- **Determinism.** Task 06 verified that **no dates or IDs leak into generated
  scaffolding** — two independent generations are byte-identical. The stamp must
  keep that: a version string only. **No generation timestamp, no commit SHA, no
  hostname.** Anything varying per run breaks the golden test's core property.
- **Golden fixtures.** Adding a line to `task-config.sh` changes all three
  fixtures (`core`, `all-layers`, `project`) — refresh with `tests/run.sh
  --update` as an intentional part of this task. It also means fixtures now
  encode a version, so **every future bump touches them**. Decide whether that's
  acceptable or whether the harness should normalise the version line before
  diffing. **Lean: normalise it** — otherwise a release bump produces a noisy
  fixture diff that hides real regressions.
- **Regeneration and drift reporting.** When regenerating over an install with
  an *older* stamp, `generate.sh` should say so ("upgrading `v0.1.0` →
  `v0.2.0`"). That is the line that would have made the missing-`inbox` drift
  self-announcing. Whether it also *refuses* on a major/breaking gap without an
  explicit flag is a separate call — `generate.sh:65` already errors on the
  Category→Worktree case, so the precedent for hard-stopping exists.
- **Existing installs read as unknown.** `captains-log`, `create-ai-builder`,
  and `second-brain` have no stamp. Their next regeneration writes one
  (`task-config.sh` is machinery — always overwritten), so no migration is
  needed; a missing stamp just means "pre-versioning".

## What to do

- [ ] Resolve the decisions above.
- [ ] Add the version source of truth and render `{{GENERATOR_VERSION}}` into
      `task-config.sh` via `src/config/task-config.sh.in`.
- [ ] Report the version in `generate.sh`'s header output (beside `epic` /
      `mount`), and report an old→new transition when regenerating.
- [ ] Refresh the three golden fixtures, and normalise the version line in
      `tests/run.sh` if that decision lands that way.
- [ ] Self-test coverage: the stamp is present and correct in a fresh install;
      two independent generations remain byte-identical; regenerating over an
      older stamp reports the transition and rewrites the value.
- [ ] Document the stamp in `src/docs/README.md` so a consumer knows where to
      look, and add "bump the version file" to the release procedure.

## Done when

A freshly generated install declares the generator version in
`task-config.sh`, regeneration over an older install reports the transition, and
generated output is still byte-for-byte reproducible.
